3부 · 요청 작성법시연

요청에는 완료 조건을 붙인다

기존 비행·배달 코드와 관련 기획 문서를 먼저 읽어 줘.

조건 밖에서 투하하면 편지를 보존하고, 조건 안에서는 한 번만 배달 완료로 처리해 줘.

완료 직후 다시 입력해도 중복 처리되지 않아야 한다.

빌드와 자동 검사를 실행하고, 바꾼 행동과 내가 직접 플레이할 항목을 알려 줘.

기획에 없는 수치는 정하지 말고 가정으로 표시해 줘.

이어서 시연(녹화본 권장): 조건 밖 투하 → 편지 보존 → 재접근 → 정상 투하. 그다음 자동 테스트 결과와 자동 경로 기준 시간을 보여준다. 비행 규칙을 바꾸지 않은 작업에서 그 숫자가 변하면 무언가 깨진 것이다. 프롬프트는 강의용으로 재구성한 예시다.

예컨대 이런 것들

  • 게임 안에서 끄는 방법이 없었다 (Alt+F4뿐)
  • 프로젝트 이름이 “Third Person Game Template”
  • 타이틀, 설정, 크레딧, 저장 실패 대비 없음

사흘 뒤 대부분의 항목: “1차 끝. 사람 확인은 남았다.”

AI에게 "출시에 필요한데 아직 없는 것"을 목록으로 만들게 했다. 항목마다 완료 기준이 한 줄씩 붙어 있다. 예: "설정을 바꾸고 껐다 켜도 유지된다." 구현과 자동 확인은 사흘(09-28~30) 만에 대부분 끝났고, 처음부터 엔딩까지 해 보는 일은 별도의 사람 확인 목록으로 남았다.
5부 · 검증 사례

직접 돌려 봐야 보이는 것

사례 1

에디터에선 안 보인다

M1 맥의 첫 Shipping 패키지가 실행되지 않았다. 템플릿의 기본 셰이더 설정 때문이었다.

사례 2

깨진 줄 모르는 세이브

저장 중 꺼지면 엔진이 반쯤 기본값으로 읽는다. 임시 파일, 백업, 교체 순서와 CRC로 바꿨다.

사례 3

세 번 만에 고친 버그

접촉음 반복. “닿아 있는가”를 “방금 닿기 시작했는가”로 질문을 바꿨다.

사례 1: 에디터는 셰이더를 그 자리에서 만들어서 문제가 드러나지 않았다. 사례 2: 자동 테스트 여섯 경우를 더하고, 실제 세이브를 반으로 잘라 복구 안내를 화면으로 확인했다. 사례 3: 첫 수정(지면 고도 기준)은 180 m 탑 위에서, 두 번째(이동 여부)는 지면을 미끄러질 때 다시 깨졌다. 틀린 것을 알려 준 것은 직접 플레이와 그때 남은 기록이다.

예상 질문. 코딩을 몰라도 되는가: 실행, 오류 재현, 변경 확인, 되돌리기는 익혀야 한다. 얼마나 빨라지는가: 비교 기록이 없어 배수로 답하지 않는다. 출시 준비 17개 항목의 1차 구현이 사흘에 끝났고 사람 확인이 그 뒤에 남았다는 기록을 보여준다. AI가 끝났다고 하면 믿어도 되는가: 완료 조건과 증거를 본다. 모든 에셋을 AI로 만드는가: 아니다. 생성 모델, 구매 에셋, 코드 합성을 일관성과 수정 가능성, 출처 기준으로 섞는다. 비용: 결제 기록을 정리한 뒤에만 숫자로 답한다.
